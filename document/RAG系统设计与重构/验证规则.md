# RAG 系统设计与重构验证规则

## 1. 适用范围

本文提供 S00～S18 共享的验证口径。具体阶段只读取和执行其需要的条目。命令必须在实际仓库中按当前模块调整，所有结果写入对应 `records/Sxx.md`，包括命令、退出码、测试数量、时间、失败项和环境差异。

## 2. 开工冻结

每个阶段至少记录：

```bash
git rev-parse HEAD
git status --short
```

构建阶段同时记录：

- `MAX(document.id)`；
- `MAX(task.id)` 和 task-log 水位；
- 当前 active parse/index task；
- 当前 KnowledgeRoute、GraphRAG、RAPTOR 和 table 产物数量；
- 应用 PID、启动时间、代码/Prompt/config hash。

对话阶段同时记录：

- `MAX(exchange.id)`；
- route/observe 表水位；
- conversation 分组和预期 exchange 数；
- 当前使用的 document/index-task cohort。

## 3. 自动验证层次

按风险从小到大执行：

1. characterization fixture；
2. 目标红灯；
3. 修改后的定向测试；
4. 受影响模块回归；
5. Java/Python 全量测试；
6. Maven package 或对应编译；
7. RAG 静态门禁；
8. `git diff --check`；
9. 需要时执行只读数据库、ES、日志和 O9 对账；
10. 需要时进入真实产品人工验收。

常用命令入口以仓库当前脚本和模块为准，优先使用：

```bash
bash scripts/rag-audit-gate.sh
bash scripts/rag-audit-gate-test.sh
git diff --check
```

Java 测试应优先使用阶段涉及模块的 `-Dtest=... test`，再执行受影响模块和全量 package。Python 测试在 `aegis-kb-rag-tools/` 中执行当前项目定义的测试命令；当前仓库可使用 `python -m unittest discover -s tests -p 'test_*.py' -v`。不要用跳过失败、删除断言或修改测试数据的方式制造绿色。

## 4. Characterization 和目标红灯

Characterization 只回答“旧实现现在做什么”，目标红灯回答“为什么这个行为违反目标契约”。二者不得混为一条断言。

每个红灯必须满足：

- 使用中性 fixture，不包含验收文档名、部门、关系名或样例词；
- 能定位到明确 producer、transition 和 consumer；
- 失败原因与目标不变量一致；
- 修改实现前稳定失败；
- 修改后通过，且相邻行为有回归保护。

### 4.1 事实等级与开工证据

阶段设计和生产修改必须把关键结论标记为以下等级：

| 等级 | 证据要求 | 使用边界 |
| :--- | :--- | :--- |
| `CONFIRMED` | 源码、测试、运行数据等多类证据交叉一致 | 可以驱动设计 |
| `CODE_CONFIRMED` | 当前源码或测试直接确认 | 可以驱动生产实现 |
| `DATA_CONFIRMED` | 数据库、日志或运行产物直接确认 | 可以驱动问题归因和验收 |
| `STRONG_INFERENCE` | 多项证据支持但缺一个直接闭环 | 只能驱动可逆验证 |
| `HYPOTHESIS` | 尚未完成核验的假设 | 不得驱动长期或不可逆实现 |

开工输出至少列出：HEAD、预存工作区、已确认事实、文档差异、证据不足项、固化旧错误的测试、拟新增 fixture 和实际修改边界。必须先找到字段、score、identity、状态的 producer，再找到聚合/映射/去重/窗口等 transition，最后确认真正作业务决定的 consumer。

### 4.2 跨阶段核心不变量

以下不变量是阶段退出时的共同检查项；具体阶段只实现自己拥有的部分：

- `RetrievalPlan` 只解释一次 hard scope、query、filter、channel、window 和 rank feature；Provider 不读取 ambient config 覆盖 Plan。
- 用户明确选择的 KB/document 是 hard scope；route、structure、entity 等 advisor 输出默认是 suggestion，只有 Plan assembler 字段级授权后才能强化。
- 每个子问题只有一个 `RetrievalExecutionRequest`，request 与 Plan 必须逐字段可对账。
- fusion 只合并候选并计算特征；rerank 只排序统一窗口；final policy 只选择 Source Evidence；Context Expansion 只产生 Context Only。
- `context_only=1` 的候选不得获得 reference ID、进入 final Source policy、成为 Prompt rendered Source 或写入最终 archive snapshot。
- Prompt rendered/reused Source identities 必须等于显式引用资格集合；最终 explicit identities 只能是该集合按合法 token 首次出现顺序形成的子集。
- 只接受合法的 1-based ASCII `[n]` token；未知、越界、非同轮和无稳定 identity 的 token 必须 fail closed。
- binding、FINALIZE 和 archive 的 source identities 必须完全同序；答案没有合法 token 时最终 identities 全为空。
- Python 返回解析结果、模型分数和算法候选；Java 决定业务 scope、route、最终证据、答案、引用、任务状态和业务库写入。
- Markdown structure/table、GraphRAG quote/lineage 和构建 outcome 失败必须保留诊断或进入 fail closed，不能以空产物或默认值伪装成功。
- 长 identity 以完整文本保存，hash 只作辅助索引；声明 row count 必须与实际持久化 row count 对账。

阶段如果发现前置阶段的不变量被新证据推翻，必须回到对应 owner 的 `REOPENED` 协议；不能在当前阶段内复制一套临时修复规则。

## 5. O9 守恒模型

每个 exchange/sub-question 至少能够沿 identity 对账：

```text
CHANNEL_RECALL
-> CHANNEL_ACCEPT
-> FUSION
-> RANKING_WINDOW
-> RERANK_REQUEST / RERANK_RESULT
-> FINAL_EVIDENCE_POLICY
-> PROMPT_RENDERED_SOURCE / PROMPT_REUSED_SOURCE
-> EXPLICIT_CITATION_ELIGIBILITY
-> CITATION_BINDING
-> FINALIZE
-> ARCHIVE
```

必查不变量：

- `context_only=1 AND is_selected=1` 必须为 0；
- 每个 ranking-window decision 有唯一 owner 和 reason；
- rerank request/result 数量、顺序、score 和状态可对账；
- rendered/reused Source identities 等于 explicit eligibility；
- explicit identities 是 eligibility 的有序子集；
- binding、FINALIZE 和 archive identities 完全同序；
- 无合法 token 时最终 identities 全为空；
- candidate persistence 实际 row count 等于声明 row count；
- identity hash 相同仍必须比较完整 identity。

## 6. 当前 rag-tools 接口事实

当前 Python 服务只提供：

| 方法 | 路径 | 职责 |
| :--- | :--- | :--- |
| GET | `/health` | 健康检查 |
| POST | `/rerank` | rerank 模型推理 |
| POST | `/document/parse` | 文档解析 |
| POST | `/graph/extract` | GraphRAG 候选抽取 |
| POST | `/raptor/build` | RAPTOR 算法构建 |

当前没有上表五个路由之外的引用处理接口，也没有 citation 专用模型配置。最终 citation 是 Java 侧显式 token 确定性绑定，不需要 Python 侧语义猜测或自动补绑。

## 7. 人工操作矩阵

| 操作 | AI 可否自动执行 | 进入前要求 | 完成后 AI 行为 |
| :--- | :--- | :--- | :--- |
| 单元/集成测试 | 可以 | 明确测试隔离范围 | 记录命令和结果 |
| 编译/静态门禁 | 可以 | 保留预存工作区 | 记录退出码 |
| 只读查询 MySQL/ES/日志 | 可以 | 已有合法连接和阶段需要 | 不修改数据 |
| 创建知识库 | 默认不可以 | 用户明确操作 | 记录 KB ID/name |
| 上传或重新上传文档 | 默认不可以 | 用户明确操作 | 只读定位新 document/task |
| 触发解析、索引、GraphRAG/RAPTOR 重建 | 默认不可以 | 用户明确操作 | 验收新产物，不混旧 task |
| 执行初始化 SQL | 默认不可以 | 用户明确操作 | 只读检查守恒 |
| 产生真实 exchange 的聊天 | 默认不可以 | 用户按清单执行 | 使用 ID 或水位定位新 cohort |

进入人工操作前，《改造计划与进度》中的状态必须为 `HUMAN_ACTION_REQUIRED`，《当前阶段与下一步》和 record 必须包含：目标 KB、文档、对话分组、精确问题、运行版本、水位、预期状态和后续只读检查。

## 8. PASS、BLOCKING_FAIL 和 OBSERVATION_ONLY

- `PASS`：确定性不变量和本阶段预期结果均满足。
- `BLOCKING_FAIL`：能够定位到本项目 scope、Plan、retrieval、build、evidence、citation、archive 或 O9 权威的确定性违规。
- `OBSERVATION_ONLY`：确定性链路合法，但模型理解、reranker 语义、回答措辞、引用覆盖或复杂综合不理想。

`OBSERVATION_ONLY` 不是《改造计划与进度》中的阶段状态，不触发阶段重开，也不能驱动样例 adapter。构建 schema、lineage、持久化或 identity 守恒失败不能降格为观察。

## 9. 静态门禁

门禁应覆盖活动 Java RAG/管理源码、Python rag-tools、Prompt、YAML 和活动改造文档。每个 finding 需要稳定 identity、classification、owner、reason 和 reviewed text。新增未分类命中必须返回非零；不得只打印计数后退出 0。

重点禁止项：

- 样例问题、文档名、部门名、金额、等级和特定关系名进入生产规则；
- Provider 读取旧会话计划或 ambient config 重新解释 Plan；
- Context 进入 final Source policy 或 citation；
- citation 相似度/NLI repair；
- 长期 compatibility facade、旧 request、旧字段和双写；
- 缺少 owner 的 O9 reason；
- 当前文档引用不存在文件或过期接口。

## 10. 收工检查

每阶段收工必须确认：

- 定向测试和受影响回归通过；
- 编译、package 和静态门禁通过；
- `git diff --check` 无输出；
- 用户预存工作区未被回滚、清理或重新 stage；
- record 已记录命令、退出码、测试数量、实际修改、证据 ID、偏差和风险；
- 《当前阶段与下一步》只保留最新继续点；
- 只有全部退出条件满足后，才在《改造计划与进度》中把阶段改为 `DONE`；
- 阶段完成后停止，不在同一会话进入下一阶段。
