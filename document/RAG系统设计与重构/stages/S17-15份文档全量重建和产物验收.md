## 阶段设计依据

旧 document/task 只代表旧 parser、旧 GraphRAG/RAPTOR 和旧表格结构，不能验证新代码。本阶段要求用户在隔离知识库中重建 15 份文档，AI 只读验收 parse/index/structure/table/graph/raptor/route 产物及其 D/P/I lineage。

本阶段所有长期设计必须由本项目的 `CODE_CONFIRMED`、`DATA_CONFIRMED`、明确不变量或目标红灯支持。外部资料只能作为一般性研究背景，不能替代本项目事实，也不进入学员版设计权威。

> 本阶段状态只在 [改造计划与进度](../改造计划与进度.md) 维护；本文件只保存阶段范围、实施清单和退出条件。全局施工与人工操作规则见 [AGENTS.md](../../../AGENTS.md)，通用命令与测试矩阵见 [验证规则](../验证规则.md)。

唯一目标：在隔离验收环境和全新 task 上从源文件重建 15 份文档，只验证构建产物，不跑完整问答。

前置阶段：S16。

必读：验收方案第 2-4 节，以及 [改造计划与进度](../改造计划与进度.md) 中“问题基线与阶段归属”和“目标架构与权威边界”的对应条目。

第一次人工操作前冻结：

- 代码 HEAD 和完整配置快照。
- 15 个源文件 checksum。
- 本次 run code、3 个 run-specific KB 名和独占 `base_id` 段。
- 原 document/task 水位。

用户完成第一次人工操作后记录：

- 用户实际创建或选定的 3 个新 KB ID。
- 15 个新 document ID 及其 parse/index task ID。

隔离规则：

- 首选独立验收数据库，在其中使用验收方案规定的 3 个 KB 名。
- 若复用现有数据库，必须使用 S16 已参数化的 run-specific KB 名和独立 `base_id` 段；不得直接用固定名称/固定 ID 的旧脚本覆盖已有 cohort。
- 3 个 KB 的文档数量必须分别为 3、6、6。

S17 的真实操作分两次人工交接：

1. AI 校验 15 个源文件、参数化配置和自动化回归，记录 document/task 水位，将阶段标为 `HUMAN_ACTION_REQUIRED`，然后由用户创建或选择 3 个隔离 KB、上传 15 份文档并触发解析、索引和派生产物构建。
2. 用户告知完成后，AI 恢复 `IN_PROGRESS` 并只读核对 15 份构建状态与产物；确认全部通过后再次标为 `HUMAN_ACTION_REQUIRED`，由用户执行 S16 已验证的参数化路由初始化脚本。
3. 用户告知脚本执行完成后，AI 再恢复 `IN_PROGRESS`，只读验收 scope、topic、relation 和 profile；不得由 AI 直接写真实验收库。

历史失败证据见 [S03 新代码真实 cohort 与阶段退出](../records/S03.md#2026-07-12-新代码真实-cohort-与阶段退出)。三个 `O8-RD-*` 是映射 `Q-O8-01/02/03` 的内部诊断，不新增验收 case。本阶段不得复用旧 chunk ID 或按旧 ID 断言通过；必须按新 document/task 的 source span、section path 和内容语义定位，并在 `records/S17.md` 记录 `内部诊断 ID -> 新 document/parse task/index task/chunk identity` 映射。

- `O8-RD-FINAL-02`：`14.1.3` 对应处理步骤的 raw Source 存在、source identity 完整并已索引，且与 `14.3.1` 并列场景保持不同 source span 和 section identity。

若新产物违反 S10 已确认语法/provenance、丢失 source span，或四项内容只剩不可引用的 `TITLE` Context，按已确认 producer 重开 S10 或 S11；若产物正确但索引缺失，保留 S17 未完成并在当前构建责任层处理。S17 只关闭构建产物，不用回答碰巧正确替代检查，也不执行三问对话。

以下命令由用户执行，并且只适用于独立验收数据库或已经注入 run-specific 参数的脚本；AI 负责准备/校验命令和参数，不负责执行：

`O2_O8_RUN_CODE` 必须与本次 3 个 run-specific KB 名中的 run code 完全一致，
`O2_O8_BASE_ID` 必须是本次 run 独占且已经只读确认无冲突的 ID 段起点。两个值和脚本必须在同一 MySQL 会话内执行：

~~~bash
export O2_O8_RUN_CODE='<本次 run code>'
export O2_O8_BASE_ID='<本次独占 base id>'

mysql -uroot -proot nexus_agent_pro <<SQL
SET @o2_o8_run_code = '${O2_O8_RUN_CODE}';
SET @o2_o8_base_id = ${O2_O8_BASE_ID};
SOURCE sql/表数据/Mysql/知识路由初始化(需要文档例子演示中文档上传解析完).sql;
SQL
~~~

脚本执行后，AI 必须只读验收 3 个 KB 的 scope、topic、topic-document relation 和 document profile 数量/归属；脚本不得修改 chunk、解析产物、KG、RAPTOR 或文档所属 KB。S18 不得在路由元数据缺失的 cohort 上开始。

### KnowledgeRoute ES 派生索引时序

`2026-07-18 CODE_CONFIRMED`：参数化 SQL 的持久化权威只有 MySQL scope/topic/relation/profile，脚本契约明确不写 ES。`ElasticsearchKnowledgeRouteIndexService.search()` 只在收到非空 routing text/entity type 后调用 `refreshIfNeeded()`，并在执行 ES search 前由 `refreshAll()` 从全部 active scope、topic 和 index-success document 同步重建 KnowledgeRoute ES，bulk 使用 `Refresh.WaitFor`。因此，在 S17 禁止聊天且 AI 禁止触发真实 route refresh 的边界内，SQL 成功后 ES 继续保留旧快照是符合当前源码的派生副本时序，不等于 MySQL 路由初始化失败。

`2026-07-18 DATA_CONFIRMED`：本 run MySQL 已形成 `3 scope / 14 topic / 15 manual profile / 26 relation` 且 ownership mismatch 为 `0`；同一时刻 KnowledgeRoute ES 仍为旧三个 KB 的 `3 scope / 14 topic / 15 document = 32` 条，本 run 为 `0`，日志没有 refresh 记录，exchange 水位未变化。S17 不为制造 ES 观测而新增对话或直接写派生索引；退出时冻结 MySQL 权威、运行时代码/config hash 和 refresh-before-search 契约。S18 首个由用户产生的非空路由请求必须在读取 route index 前同步刷新，并只读确认全局 `65` 条、本 run `32` 条及 `3/14/15` 类型分布；若未满足，再按实际 producer 归属处理，不能用手工 ES 写入制造通过。

产物门槛：

- 15/15 `parse_status=3`、`strategy_status=3`、`index_status=3`，task ID 非空。
- `document.last_parse_task_id` 和 `last_index_task_id` 都必须联到 `nexus_agent_document_task.task_status=3`，不能只看 document 上的三个状态字段。
- 任务成功以外，还要检查 chunk/parent、structure、table/row/cell、KG/evidence/community、RAPTOR/source 下钻和 PG/ES 索引数量。
- 星联结构 depth/parent 正确。
- 四份核心 Markdown table 正确。
- Graph relation quote 指向当前 task chunk，无 orphan。
- `nexus_agent_raptor_node.task_id = document.last_index_task_id`；summary-only 不具 citation capability，并通过运行时 selected/source identity 验证 source parent 确实下钻 raw chunk，不能只凭 node 数量通过。
- 3 个验收 KB 的 scope/topic/relation/profile 初始化成功并指向本 cohort 的新 document/task。
- MySQL route 权威完整指向本 cohort；KnowledgeRoute ES 服从上方已确认的 refresh-before-search 时序，S17 不越过人工聊天边界预触发刷新。GraphRAG 跨文档派生索引基于本 cohort 的新 task。

规则：

- 不复用旧 document/task ID 证明通过。
- 真实 KB 创建/选择、文档上传、解析/索引/重建触发和初始化脚本执行均由用户完成；AI 不通过浏览器、接口、脚本或数据库写入代替。
- 禁止手工修改 document/task/current pointer、KG evidence 或 route relation 来制造绿色结果。
- 禁止为了让 KnowledgeRoute ES 提前出现本 run 而在 S17 触发聊天、调用隐含 refresh 的业务接口或直接写 ES；实际刷新和 `65/32` 只读验收随 S18 首个合法新 exchange 进行。
- 不在本阶段现场补 parser/Graph/table 业务规则。
- 产物失败时标记对应 S10-S14 或 S03 为 `REOPENED`，记录失败 task，然后停止。
- 所有 15 份产物通过后才允许进入 S18。
- S17 开始后如果任何构建代码或构建配置发生变化，本次 15 文档 cohort 整体失效，必须从新 task 重新构建。
