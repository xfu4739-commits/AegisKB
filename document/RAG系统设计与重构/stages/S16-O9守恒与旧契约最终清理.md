## 2026-07-19 重开：可变长 citation identity 与观测持久化结果

S18 首个新 exchange `2346519957279350785` 冻结了 S16 原退出条件未覆盖的真实反例：两个子问题的 channel execution recalled/accepted 均为 `27/27`，但第二个子问题包含合法的 284 字符 `TABLE:<tableId>:CELLS:[<cellIds...>]` citation identity；它写入 `nexus_agent_chat_retrieval_result.citation_identity VARCHAR(255)` 时触发 `Data too long`，使该子问题 27 行在一个事务中整体回滚。`ConversationTraceRecorder` 只记 WARN 后继续回答，因此 route、答案、Prompt、binding/final/archive 均正确时，O9 raw-observation 仍可 false green。该反例推翻的是 S16 O9 派生投影的 schema、事务结果和验收门禁，不改变 S12 table identity、S09 candidate/selection 或 S02 citation binding 权威，也不要求重做 S17 构建产物。

修复契约：

- canonical `citationIdentity` 继续由 `EvidenceIdentityResolver` 完整生产并作为业务比较权威；不得把 fusion、rerank、Prompt、binding、FINALIZE 或 archive 的 identity 替换为 hash。
- `nexus_agent_chat_retrieval_result` 是可重建的 O9 派生投影。完整 `citation_identity` 使用 `MEDIUMTEXT`；另存其 UTF-8 字节的 lowercase SHA-256 hex 到 `citation_identity_hash CHAR(64) CHARACTER SET ascii COLLATE ascii_bin`。identity 为空时 hash 为 NULL；identity 非空时 hash 必须存在且与完整值相符。
- 删除完整长文本上的旧普通索引，新增 `(exchange_id, sub_question_index, citation_identity_hash)` 索引。hash 只缩小索引候选；任何精确 identity 查询都必须同时比较 `citation_identity_hash` 和完整 `citation_identity`，不得把 hash 相等解释成业务 identity 相等。
- schema 演进必须同时更新新建库 DDL 和保留在仓库中的一次性 migration。上线顺序固定为停止旧 Java writer、执行 migration/backfill、确认完整 identity 与派生 hash mismatch 为 `0`、构建并启动新代码；backfill 必须按完整 identity 重算所有 NULL 或错误 hash，派生 hash 漂移也能用同一表达式修复。AI 不直接对真实业务 MySQL 执行 migration。
- 每个 sub-question 的 retrieval-result 批次仍是单一事务原子点；成功必须返回实际持久化行数并与 expected candidate count 相等，异常或行数不等必须记为失败。观测投影失败继续 fail-open，不使正确回答失败，但不得只记日志。
- `RAG_RETRIEVE` 和 `EVIDENCE_BUDGET.subQuestions[]` 必须投影同一 producer 返回的 `observationPersistence={schemaVersion,status,expectedCandidateCount,persistedCandidateCount,errorType}`。`status` 只允许 `SUCCESS/FAILED/NOT_ATTEMPTED`；实际运行中有 recorder 的正常零候选批次为 `SUCCESS 0/0/NONE`，写入成功为 `SUCCESS n/n/NONE`，异常或行数不等为 `FAILED` 且 errorType 非 `NONE`。`NOT_ATTEMPTED` 只描述没有 recorder 的非持久化调用边界，不能作为真实 cohort 通过状态。
- `errorType` 只允许 `NONE/NO_RECORDER/RETRIEVAL_FAILED/OBSERVATION_PROJECTION_ERROR/DATA_INTEGRITY_VIOLATION/VALIDATION_ERROR/ROW_COUNT_MISMATCH/PERSISTENCE_ERROR`。`SUCCESS` 只能配 `NONE`；`NOT_ATTEMPTED` 只能配 `NO_RECORDER`；其余非 `NONE` 类型只能配 `FAILED`。未知值、缺值或非法组合必须 fail closed。
- S16/S18 真实 cohort 的每个 sub-question 都必须先断言 observation persistence schema 存在且为 `SUCCESS`，再按 `(exchange_id, sub_question_index, channel_type)` 对账 channel/raw 行；缺字段、FAILED、NOT_ATTEMPTED、expected/persisted 不等或 candidate 行缺失均为 `BLOCKING_FAIL`，不得因其他链路正确而降级为 observation-only。

## REOPENED 门禁数据源与非嵌套移交

S16 是已确认 audit gate 缺陷的唯一 owner：前置 owner 因新证据成为 `REOPENED` 时，已真实完成的后继阶段可以保留历史状态；当前门禁无条件要求所有 successor 为 `NOT_STARTED`，会误报 `CURRENT_STAGE_SUCCESSOR_STARTED`。唯一判定数据源固定为 改造计划与进度 状态表旁的 `rag-stage-reopen-baseline.v1`，S00 不再作为并行 owner。

- 正常 active descriptor 必须包含 `ownerStage`、`ownerPreviousStatus=DONE`、`previousCurrentStage`、带时区 ISO-8601 `reopenedAt` 和按阶段顺序排列的完整 `successorBaseline=[{stage,status}]`。`ownerPreviousStatus` 证明这是完成后被新证据推翻，而不是把 `NOT_STARTED/IN_PROGRESS` 错标为 `REOPENED`。
- active descriptor 必须覆盖 owner 的完整返工周期：descriptor 非空时 `currentStage=ownerStage`，owner 当前状态只允许 `REOPENED/IN_PROGRESS/HUMAN_ACTION_REQUIRED/BLOCKED`；owner 在这些状态间按 改造计划与进度 合法流转时 descriptor 必须保留，且 successor 在每一种 owner 状态下都必须与 baseline 完全一致。只有 owner 原子进入 `DONE`、currentStage 恢复为 `previousCurrentStage` 时才允许清空 descriptor。
- 初始 baseline 自身必须符合正常阶段顺序：owner 到 `previousCurrentStage` 之前全为 `DONE`，执行前沿可为 `NOT_STARTED/IN_PROGRESS/HUMAN_ACTION_REQUIRED/BLOCKED`，其后全为 `NOT_STARTED`，不得含 `REOPENED`。重开期间每个 successor 必须与 baseline 逐项相等；`BLOCKED` 必须作为合法前沿状态进入正向 fixture。
- 禁止同时存在两个 active reopen。active owner A 又确认更早 owner B 错误时，门禁只接受 改造计划与进度 定义的一次原子移交：A descriptor 移入唯一 `suspendedReopen`、A 状态变为 `BLOCKED`、B 以 `ownerPreviousStatus=DONE` 激活；B baseline 中 A 必须为 `BLOCKED`，A 之后必须与 suspended baseline 相等。B 完成后原子恢复 A descriptor 和 `REOPENED` 状态并清空 suspended。已有 suspended 时再次发现更早 owner，不得继续堆栈；active owner 进入 `BLOCKED` 并停止，等待显式状态审查。
- 缺失/重复元数据、schema/owner/currentStage/ownerPreviousStatus 不一致、不完整或乱序 successor、非法 baseline 顺序、transfer/suspended 关系不守恒、任一后继状态推进/回退、普通状态残留 reopen metadata 都必须 fail closed。records、Git 历史、文件时间和自然语言日期不得参与判定。

S04 转入门禁债务：逐项审计 `DocumentProfileServiceImpl` 构建期 document-profile 本地词表的十个 finding，区分通用 enrichment 与验收样例特化。允许保留的构建期 enrichment 必须有通用输入、持久化产物和消费边界证据；任何本地词表都不得泄漏为运行时 route、channel 或 final evidence 规则，也不得未经逐项核验批量标记为 allowed。

规则：

- `CODE_CONFIRMED`：当前主链为每个 `RetrievalExecutionRequest` 独立执行 fusion/rerank/final policy，全部 `SubQuestionEvidence` join 后才为 exchange 写一条 `EVIDENCE_BUDGET`。最终 schema 因此必须是一条 exchange snapshot 内的 `subQuestions[]` 分组，而不是 exchange 顶层的无 scope candidate 数组。`subQuestionCount` 必须等于 execution request 数和 block 数；`subQuestionIndex` 为正数、唯一，block 按 index 升序，index 集合与 execution request 完全相等。window/candidate/request/result/transition/decision 的唯一性和外键只在所属 block 内判断。
- `candidateId` 是一个物理运行时候选始终存在、在所属 `(exchangeId, subQuestionIndex)` 内唯一且生命周期内稳定的身份；每个 producer 创建新候选时分配，不能由列表 index、rerank rank 或 citation capability 临时推导。channel 层 `candidate_id` 对账原始候选，producer 创建的新候选通过同 block `identityTransitions` 连接前后 candidate ID；不同 block 可合法复用相同 candidate ID。
- `lineageIdentity` 是始终存在、仅用于 lineage/O9 的非能力身份；`identityResolutionStatus` 只允许 `CITATION_RESOLVED`、`CONTEXT_RESOLVED`、`CANDIDATE_FALLBACK`，对应值必须分别为 `CITATION:<citationIdentity>`、`CONTEXT:<contextIdentity>`、`CANDIDATE:<candidateId>`。fallback 不能留空、在同 block 复用或授予引用能力。`citationIdentity` 可空且只表示已通过 capability 边界的 Source 引用身份；只有它可以参与 final policy citation 去重、Prompt reference、explicit citation binding 和 final citation。sub-question `evidenceLineage.*EvidenceIdentities` 保留检索语义集合，exchange 顶层只保存 Prompt/citation 之后的 manifest、rendered/eligible 和 binding 集合；两者不得互相替代物理 candidate ledger。
- `requestCandidateId` 只在所属 sub-question 的一次 rerank 协议请求内做 correlation，与稳定 `candidateId` 一一映射；不得把请求顺序、协议 ID 或结果 rank 回写为 candidate ID。
- retrieval result 是 channel raw observation 账本，不是 fusion/window/policy 物理候选账本。同一 policy-selected `citationIdentity` 可以对应多个 channel 的不同 raw `candidate_id`，因而可以出现多条 `is_selected=1`；这是 selected identity/final rank 对 raw observation 的投影，不会产生额外 final decision。不得对 retrieval row 按 citation identity 去重后冒充 raw cardinality，也不得将 raw row 总数冒充 candidate/decision cardinality。
- 每个 `(exchangeId, subQuestionIndex, channelType)` 内 `recalled_count = retrieval_result raw 行数`，`accepted_count = gate_passed=1 的 raw 行数`，`final_selected_count = gate_passed=1 AND is_selected=1 的 raw 行数`。该组内对账不引用 `finalEvidenceDecisions[]`。
- candidate/window/final decision 守恒只能在每个 `subQuestions[]` block 内按稳定 `candidateId` 完成；不同 block 可重复 candidate ID，不得跨 block distinct，也不得与 retrieval raw observation 行做直接基数等式。
- 每个 block 的 `sourcePartitionCandidateIds` 必须由 Source/Context partition producer 按稳定 fusion Source 顺序产生，并与 `sourceRankingWindowDecisions[].candidateId` 按基数和集合完全相等。两个数组都按该顺序持久化；各自 `FOR ORDINALITY`、按 candidate ID 关联的 partition ordinality 与 decision `inputRank` 必须相等且从 1 连续。每个 partition Source 恰有一条 producer-owned window decision。
- `RetrievalPlan.rerankWindow` 必须在 assembly 阶段 fail-fast 校验为 `0 < rerankWindow <= candidateWindow`；零值或负值不得进入运行时 window。唯一 window owner 只做 `FUSION_INPUT_ORDER` 的前缀截取，不得重排、重算 score、打破同分、按 citation capability 过滤或产生第二选择权威。该 cap 无论 `rerankRequested` 为 true 或 false 都必须应用，所有 decision 的 `cap` 都必须等于 plan 值。

正常 window build 使用以下双向真值表：

| `inputRank` 条件 | `disposition` | `reason` | `windowRank` |
| :--- | :--- | :--- | :--- |
| `inputRank <= cap` | `INCLUDED` | `INCLUDED_IN_SOURCE_RANKING_WINDOW` | `inputRank` |
| `inputRank > cap` | `FILTERED` | `FILTERED_BY_SOURCE_RANKING_WINDOW_CAP` | `null` |

- 正常 build 必须满足 `includedCount = min(sourcePartitionCount, cap)`，上述每列组合都使用“当且仅当”，且 build-failure reason 计数为 0。partition IDs 必须被 included/filtered 无损、不重叠地分解；不得过滤前 cap 内 Source、纳入 cap 后 Source 再重排 rank。
- included candidate ID 集合必须与同 block `sourceRankingWindowCandidates[].candidateId`、`finalEvidencePolicyInputCandidateIds`、`finalEvidenceDecisions[].candidateId` 按基数、顺序和集合完全相等；`sourceRankingWindowCandidates[].lane` 只能是 `SOURCE`。`candidateIndex` 从 0 连续、唯一，并与 policy 输入顺序一致。非 citation-capable Source 允许 `citationIdentity` 为空，但 `candidateId/lineageIdentity/identityResolutionStatus` 不得为空；window owner 不得按 citation capability 提前过滤前 cap 候选，能力不足必须由 final policy fail closed。filtered candidate 与 ranking/request/result/policy/final decision 集合全部不相交，window reason 不得重写为 final policy reason。

异常与空输入使用以下真值表：

| 场景 | window decisions | included/ranking/policy/final | `rerankExecution` |
| :--- | :--- | :--- | :--- |
| Source 非空、build failure、`rerankRequested=true` | 全部 `FILTERED/FILTERED_BY_SOURCE_RANKING_WINDOW_BUILD_FAILURE/windowRank=null` | 全部为空 | `FAILED_BEFORE_REQUEST/WINDOW_BUILD_FAILED/WINDOW_BUILD` |
| Source 非空、build failure、`rerankRequested=false` | 全部 `FILTERED/FILTERED_BY_SOURCE_RANKING_WINDOW_BUILD_FAILURE/windowRank=null` | 全部为空 | `NOT_REQUESTED/PLAN_DISABLED/NONE` |

| Source 为空、`rerankRequested=false` | partition 与 decisions 均为空 | 全部为空 | `NOT_REQUESTED/PLAN_DISABLED/NONE` |

- build failure 的 decision 仍保留与 partition ordinality 相同的 `inputRank`、合法 cap 和 `FUSION_INPUT_ORDER`，不得混入 `INCLUDED` 或 cap-filter reason。每个 block 的 `contextDispositionCandidateIds` 必须由同一 partition 的 Context 输出边界产生，并与该 block Source partition、window decision、Source ranking window、rerank request、rerank result、policy input 和 decision candidate ID 集合全部不相交。只有 Source partition 本身为空时 window decision 和后续集合才能全部为空；cap 过滤或 build failure 不能冒充空 Source。
- `rerankRequestCandidates` 只在完整 payload 原子交给 transport gateway、`attempted=true` 时产生，数组内 `requestCandidateId/candidateId` 分别唯一并一一映射；`rerankResultCandidates` 只能由实际响应解析边界产生，其 pair 必须引用同 block request ledger，不能从 `RERANK_SCORE`、最终排序或 decision 反推。`resultStatus` 只允许 `FINITE`、`NON_FINITE_TO_ZERO`、`UNUSABLE`；`FINITE` 保存有限 score，`NON_FINITE_TO_ZERO` 保存 JSON 可表达的 score `0` 并由 status 保留归零事实，仅这两项可被 policy 消费；`UNUSABLE` 的 score/rank 为空。
- `RetrievalPlan.rerankRequested` 是 rerank intent 的唯一权威：`ChatRagProperties.isRerankEnabled()` 只允许由 `RagRuntimeOptions.from(ChatRagProperties)` 在配置归一化边界读取，normalized `RagRuntimeOptions.isRerankEnabled()` 只允许由 `RetrievalPlanAssembler.assemble()` 读取并冻结进 plan；normalized option 和 `from(null)` 的默认值必须保持 true，不能落入 boolean/builder 的隐式 false。getter/field 定义不计作 consumer，engine/orchestrator/rerank service/final policy/store/O9 的两类 ambient getter 调用必须为 0。`rerankExecution.requested` 必须是 plan 字段的纯投影，且 `requested=false` 当且仅当 `status=NOT_REQUESTED`。`attempted=true` 当且仅当完整 payload 已交给 transport gateway。状态按 plan intent -> 正常 Source window 空否 -> pre-request 准备 -> transport attempt -> 完整 response 校验依次判定：

| `status` | `requested` | `attempted` | window / `finalEvidenceDecisions[].scoreProvenance.rerankStatus` | request/result ledger | `reason` / `failureStage` |
| :--- | :---: | :---: | :--- | :--- | :--- |
| `NOT_REQUESTED` | false | false | cap/window decision 严格服从上述正常、build-failure 或空 Source 真值表；included/policy/final 集合相等，所有现存 `finalEvidenceDecisions[].scoreProvenance.rerankStatus=NOT_REQUESTED` | 均为空 | `PLAN_DISABLED` / `NONE` |
| `SKIPPED_EMPTY_SOURCE_WINDOW` | true | false | Source partition、window decision、ranking/policy/final 集合都为空 | 均为空 | `EMPTY_SOURCE_WINDOW` / `NONE` |
| `FAILED_BEFORE_REQUEST` | true | false | `WINDOW_BUILD_FAILED` 时已有 Source 全部 window-filtered 且 included/policy/final 为空；其余 pre-request 失败时 included/policy/final 集合相等，所有 `finalEvidenceDecisions[].scoreProvenance.rerankStatus=FAILED` | 均为空 | 受控失败 reason / `WINDOW_BUILD` 或 `PRE_REQUEST` |
| `FAILED_AFTER_REQUEST` | true | true | window decision 完整，included/policy/final 非空且集合相等，所有 `finalEvidenceDecisions[].scoreProvenance.rerankStatus=FAILED` | request candidate 集合等于完整 included window；result 为空或只含 `UNUSABLE` | 受控失败 reason / `TRANSPORT` 或 `RESPONSE_VALIDATION` |
| `SUCCESS` | true | true | window decision 完整，included/policy/final 非空且集合相等，所有 `finalEvidenceDecisions[].scoreProvenance.rerankStatus=SUCCESS` | request/result candidate 集合都等于完整 included window，每个 request ID 恰有一个可消费 result | `NONE` / `NONE` |

- `reason` 只允许 `NONE`、`PLAN_DISABLED`、`EMPTY_SOURCE_WINDOW`、`WINDOW_BUILD_FAILED`、`PROVIDER_UNAVAILABLE`、`CIRCUIT_OPEN`、`INVALID_CONFIGURATION`、`CLIENT_INITIALIZATION_FAILED`、`REQUEST_VALIDATION_FAILED`、`CANCELLED`、`TRANSPORT_ERROR`、`TIMEOUT`、`PROVIDER_ERROR`、`INVALID_RESPONSE`、`PARTIAL_RESULT`，并必须与上表 status 相容。`failureStage` 只允许 `NONE`、`WINDOW_BUILD`、`PRE_REQUEST`、`TRANSPORT`、`RESPONSE_VALIDATION`。映射固定为：`WINDOW_BUILD_FAILED -> WINDOW_BUILD`；provider/circuit/config/client/validation 原因 `-> PRE_REQUEST`；transport/timeout/provider error `-> TRANSPORT`；invalid/partial response `-> RESPONSE_VALIDATION`；`CANCELLED` 在 request handoff 前只能是 `WINDOW_BUILD/PRE_REQUEST`，handoff 后只能是 `TRANSPORT`。正常三态的 failureStage 必须为 `NONE`。plan 禁用但 window build 失败时 rerank execution 仍为 `NOT_REQUESTED/PLAN_DISABLED`，由 window decision 保存失败；plan 请求时才映射为 `FAILED_BEFORE_REQUEST/WINDOW_BUILD_FAILED`。部分结果必须整批 `UNUSABLE` 后 fail closed 或使阶段失败；空 included set 不能自动解释成空 Source 或成功。O9 汇总层不得从 `RERANK_SCORE` 或集合差猜测 execution、attempted、reason、window disposition、request 或 result。
- 每个 block 的 final evidence policy 输入恰有一条 decision，`owner` 只能是 `FINAL_EVIDENCE_POLICY`，reason 必须唯一；selected decision 必须有 block 内唯一、连续的正 `finalRank`，filtered decision 的 `finalRank` 必须为空。
- 每个 block selected decision 的非空 `citationIdentity` 集合必须等于同 block `budgetSelectedSourceIdentities`；Context candidate/context identity 不得出现在同 block `finalEvidencePolicyInputCandidateIds` 或 `finalEvidenceDecisions` 中。不同 block 可重复同一 citation identity；顶层 `referenceManifest` 必须用 `subQuestionIndex + inputOrdinal` 保存输入归属和多重性，不能用 exchange 级 `distinct` 代替 per-sub-question 守恒。exchange 顶层不得另存一个可被误作权威的 `BUDGET_SELECTED_SOURCE` identity 数组；数据库同名 selection state 通过 retrieval row 的 `sub_question_index` 与 block 对账。
- 每个 block 的 `identityTransitions` 是该 sub-question 全部 identity/lineage 基数变化的通用账本，必须作为数组 key 存在。允许类型仅为 `FUSION_DEDUPLICATION`、`PARENT_ELEVATION`、`CONTEXT_EXPANSION`，对应 stage 仅为 `FUSION`、`PARENT_ELEVATION`、`CONTEXT_EXPANSION`；transition 必须由实际 producer 产生，汇总层不得事后推断。
- `transitionId` 在所属 block 内唯一，数据库语义键为 `(exchangeId, subQuestionIndex, transitionId)`；`inputCardinality/outputCardinality` 分别等于 `fromCandidates/toCandidates` 元素数。各端 endpoint 的 `candidateId/lineageIdentity/identityResolutionStatus` 非空，candidate ID 在数组内唯一；已解析 lineage identity 允许在不同 candidate ID 间重复以真实表达 dedupe/elevation，`CANDIDATE_FALLBACK` 必须在 block 内按 candidate ID 唯一。端点必须出现在同 block 相应 producer 输入/输出 lineage 中；fusion 不得因 citation identity 为空而合并两个 fallback 候选。只有该 block 的 fusion、parent elevation、context expansion 都没有改变 identity 或基数时数组才允许为空，是否 direct rerank 与空数组无关。
- Parent Context 与 Source identity 必须物理独立；Parent/Context score projection、跨 identity relevance 对象、projected metadata key、projected `scoreSource` 和 score-projection transition type 均为不守恒。真实 Source 只能以自身 candidate identity/text 直接参加 rerank。
- 每条 final decision 必须有 `scoreProvenance`，且 `scoreProvenance.sourceCandidateId` 等于同一 decision 的 `candidateId`。`scoreSource` 只允许 `RERANK_SCORE`、`HYBRID_SCORE`、`SCORE`、`DOCUMENT_SCORE`、`NONE`；`kind` 只允许 `DIRECT_CANDIDATE_SCORE`、`ZERO_FALLBACK`；`stage` 只允许 `RERANK`、`FUSION`、`RETRIEVAL`、`FINAL_EVIDENCE_POLICY`；`normalization` 只允许 `NONE`、`NON_FINITE_TO_ZERO`、`MISSING_TO_ZERO`；`rerankStatus` 只允许 `SUCCESS`、`FAILED`、`NOT_REQUESTED`。
- 每个 final policy input Source 必须有且只有一个由 rerank orchestration 按同 block request/result ledger 显式产生的 decision `rerankStatus`：execution `SUCCESS` 映射 `SUCCESS`，`FAILED_BEFORE_REQUEST/FAILED_AFTER_REQUEST` 映射 `FAILED`，`NOT_REQUESTED` 映射 `NOT_REQUESTED`；`SKIPPED_EMPTY_SOURCE_WINDOW` 没有 policy input/decision。缺失或未知状态不得被 policy 或 O9 投影层猜成 `NOT_REQUESTED`。
- `RERANK_SCORE` 必须对应 `DIRECT_CANDIDATE_SCORE/RERANK/SUCCESS`；`HYBRID_SCORE` 与 `SCORE` 对应 `DIRECT_CANDIDATE_SCORE/FUSION`；`DOCUMENT_SCORE` 对应 `DIRECT_CANDIDATE_SCORE/RETRIEVAL`；`NONE` 对应 `ZERO_FALLBACK/FINAL_EVIDENCE_POLICY/MISSING_TO_ZERO`。rerank 失败后使用较低层分数或 `NONE` 必须记录 `FAILED`，未请求时记录 `NOT_REQUESTED`；`SUCCESS` 不得与 `NONE` 或较低层 score source 组合。有限 direct score 使用 `normalization=NONE`；较高层非有限值保持 `DIRECT_CANDIDATE_SCORE` 和原 source/stage、以 `NON_FINITE_TO_ZERO` 归零且不得回退。`scoreProvenance` 不得出现 `transitionId`。
- `RERANK_SCORE/SUCCESS` decision 必须在所属 block 按同一 candidate ID 外键到唯一 request/result pair；result `FINITE` 对应 `normalization=NONE`，result `NON_FINITE_TO_ZERO` 对应 `normalization=NON_FINITE_TO_ZERO` 和 `relevanceScore=0`。`FAILED/NOT_REQUESTED` decision 不得外键到可消费 result，也不得消费残留 `RERANK_SCORE`。

~~~sql
WITH expected_exchange(exchange_id) AS (
    SELECT CAST(:evidence_exchange_id AS UNSIGNED)
    UNION ALL
    SELECT CAST(:no_parsed_token_exchange_id AS UNSIGNED)
~~~

~~~sql
    LEFT JOIN nexus_agent_chat_exchange e
      ON e.id = x.exchange_id
     AND e.id > :exchange_watermark
~~~

~~~sql
    SELECT s.exchange_id, j.ord, j.evidence_id
    FROM cohort c
    JOIN nexus_agent_chat_exchange_trace_stage s
      ON s.exchange_id = c.exchange_id
     AND s.stage_code = 'CITATION_BINDING'
     AND s.status = 1,
         JSON_TABLE(
           s.snapshot_json,
           '$.sourceSnapshotIdentities[*]'
           COLUMNS (
             ord FOR ORDINALITY,
             evidence_id VARCHAR(512) PATH '$'
           )
         ) j
), archive_ids AS (
    SELECT c.exchange_id, j.ord, j.evidence_id,
           j.context_only, j.generation_visible
    FROM cohort c,
         JSON_TABLE(
           COALESCE(c.source_snapshot_list, JSON_ARRAY()),
           '$[*]'
           COLUMNS (
             ord FOR ORDINALITY,
             evidence_id VARCHAR(512) PATH '$.citationIdentity',
             context_only BOOLEAN PATH '$.contextOnly',
             generation_visible BOOLEAN PATH '$.generationVisible'
           )
         ) j
)
SELECT
  (SELECT COUNT(*) FROM binding_ids b
   LEFT JOIN archive_ids a
     ON a.exchange_id = b.exchange_id
    AND a.ord = b.ord
    AND a.evidence_id = b.evidence_id
   WHERE a.evidence_id IS NULL)
  +
  (SELECT COUNT(*) FROM archive_ids a
   LEFT JOIN binding_ids b
     ON b.exchange_id = a.exchange_id
    AND b.ord = a.ord
    AND b.evidence_id = a.evidence_id
   WHERE b.evidence_id IS NULL)
  +
  (SELECT COUNT(*) FROM archive_ids
   WHERE evidence_id IS NULL
      OR NOT (context_only <=> FALSE)
      OR NOT (generation_visible <=> TRUE))
  AS binding_archive_order_or_visibility_mismatch;
~~~
