## 阶段设计依据

代码和构建产物通过后仍需在固定版本、新 exchange 和 S17 当前 task 上完成产品终验。本阶段执行 48 个唯一 case，分别检查 hard scope、Plan/request、候选与窗口、Prompt/citation、archive 和 O9，并将模型质量问题与确定性 blocker 分开。

本阶段所有长期设计必须由本项目的 `CODE_CONFIRMED`、`DATA_CONFIRMED`、明确不变量或目标红灯支持。外部资料只能作为一般性研究背景，不能替代本项目事实，也不进入学员版设计权威。

> 本阶段状态只在 [改造计划与进度](../改造计划与进度.md) 维护；本文件只保存阶段范围、实施清单和退出条件。全局施工与人工操作规则见 [AGENTS.md](../../../AGENTS.md)，通用命令与测试矩阵见 [验证规则](../验证规则.md)。

唯一目标：基于 S17 新产物，用全新 exchange 执行验收方案中的 48 个唯一 Q 编号并给出最终完成判定。

前置阶段：S17。

开工前：

- 确认验收方案可提取 48 个唯一编号。
- 固化分组数量：O2=3、O8=16、ROUTE=7、O3=4、O6=7、O7=4、TABLE=7，总计 48。
- 明确 48 个 case ID 只有 44 个唯一问题文本：O3-01=ROUTE-07、O3-02=ROUTE-03、O3-03=TABLE-04、O3-04=O6-04；四个 O3 case 仍要在 O3 专用对话产生独立 exchange。
- 确认 Q-TABLE-04 的直接问题事实是北京/一线城市 500 元、其他城市 350 元；原表中的新一线 450 元用于完整性观察，问题未明确询问时遗漏该分类不构成阻断。
- 冻结项目 HEAD、Java/rag-tools PID、运行时代码、Prompt 和配置 hash；任一项与 S17 冻结值不同都必须先说明影响，不能直接沿用 S17 cohort。
- 记录 exchange watermark。
- 在首个 exchange 前只读重算 MySQL 当前 active scope/topic/index-success document 的全局和本 run 输入，保存 KnowledgeRoute ES 本轮应有的总数与类型分布；S17 结束时的全局 `65`、本 run `32`、本 run 类型 `3/14/15` 只是无合法数据变化时的冻结参考值，不是永久常量。
- 为不同连续追问链明确会话分组，避免历史串题。

人工交接分两轮执行。AI 先准备 48 个 case 的问题、顺序、会话分组、产品入口要求和操作前 exchange watermark，并选择一个不依赖前置上下文、能够触发非空 route search 的 case 作为首轮；将 S18 标为 `HUMAN_ACTION_REQUIRED` 后停止。用户只执行该首个真实 exchange，AI 恢复 `IN_PROGRESS` 并先完成下节 KnowledgeRoute ES 只读审计；审计通过后该 exchange 才纳入 S18 cohort，AI 再次把 S18 标为 `HUMAN_ACTION_REQUIRED`，由用户执行其余 47 个 case。全部真实对话都必须由用户通过实际产品入口执行，AI 不调用浏览器自动化、聊天 HTTP 接口、脚本或数据库写入制造 exchange。用户完成每轮人工操作后，AI 依据用户提供的 exchange ID 或事前水位只读查询数据库、O9 stage snapshot、检索结果和日志并逐项判定。

每个 case 的判定只允许：`PASS`、`BLOCKING_FAIL`、`OBSERVATION_ONLY`。`BLOCKING_FAIL` 只用于本项目可由源码和运行数据稳定定位的确定性 authority/invariant 违规，例如 hard scope 越界、suggestion 越权硬化、普通召回被可选增强清空、唯一 ranking/final-policy 违反明确排序或窗口契约、错误构建产物被权威链路消费、Source/Context 或 token 绑定越界，以及 binding/FINALIZE/archive identity 不守恒。LLM query understanding、multi-turn refinement、reranker 模型和答案生成导致的答反、漏项、措辞、表格分类/行数口径、citation 语义覆盖不足或复杂关系综合，只要 scope、Plan/request、证据可见性、citation authority 和 O9 守恒均合法，一律记 `OBSERVATION_ONLY`。确定性工程链路不能保证这些模型质量问题，本项目不得因此重开阶段、增加本地语义 adapter 或恢复 citation NLI repair。

必须覆盖：

- O3 rerank、O4 citation、O6 GraphRAG、O7 RAPTOR、table 和 O9。
- 48 个唯一编号每个都有新的 exchange ID、答案判定和证据链记录，不能用“总轮数接近”替代覆盖。
- O8-01 至 O8-16 保持验收方案原顺序和规定的会话链；“还有”“这个问题”“刚才”等追问不能拆成无历史的独立问题。

## KnowledgeRoute ES 首轮接力

MySQL active scope/topic/index-success document 是 KnowledgeRoute 路由持久化权威，ES 是非空 route search 前通过 `refreshIfNeeded -> refreshAll` 重建的派生副本。S18 不把 S17 结束时冻结的 `65/32` 写成永久通过条件：首轮人工操作前必须只读重算当前 MySQL 输入并在 `records/S18.md` 记录查询时间、全局 scope/topic/document 数、本 run scope/topic/document 数、求和结果及相对 S17 冻结值的变化原因。

- 如果没有合法数据变化，刷新后预期仍为全局 `6/28/31=65`、本 run `3/14/15=32`。
- 如果存在可解释的合法数据变化，必须按当前 MySQL 权威输入重算本轮 ES 预期并记录原因；不得为了匹配 `65/32` 修改 MySQL 或手工写 ES。
- 首个用户产生的非空 route exchange 完成后，必须先只读确认 refresh 日志存在、ES 全局总数等于本轮重算值、本 run 总数及 scope/topic/document 分布等于本轮重算值，且没有 KB ownership 或 run 归属异常。
- 只有上述审计通过，首个 exchange 才能纳入 48 case cohort 并继续其余 case。审计失败时停止后续人工对话，保留 S18 的当前普通阶段状态并先核对路由请求是否确实非空、日志/查询口径、运行依赖和真实 producer；禁止直接写 ES 制造通过。

## 表格终验的确定性边界

S18 使用 S17 当前 document/task 产物核对 table schema/grid/source identity、Plan/request scope、candidate ledger、Prompt visibility 和 citation/O9 守恒。只有这些确定性 producer/transition/consumer 违反现行契约时才路由到 S12/S17、S07-S09、S01 或 S02。

- 单个问法没有触发 table operation、table channel 为 0、表头是否计入行数、模型未覆盖未明确询问的分类，或合法 citation 对答案事实覆盖不足，均属于 `OBSERVATION_ONLY`；不能仅凭最终答案或某个 channel 为 0 推翻已确认的 table 构建契约。
- Q-TABLE-04 直接询问北京和其他城市，`500/350` 是直接问题事实；新一线 `450` 是更完整回答的观察项。遗漏 `450` 本身不产生 S15/S12 owner。
- table/row/cell 产物缺失或 identity 错误、受控 hard scope/filter 确定性排除合法产物、已选 Source 未进入 Prompt、Context/未渲染 Source 或非法 token 被绑定，以及 binding/FINALIZE/archive 不守恒，才是 `BLOCKING_FAIL`。
- S18 不现场增加问题词、列值同义词、Prompt 规则、adapter、权重或 topK，也不恢复 NLI 作为 citation 业务决策者。

三问还必须满足现行 Source/Context 与 explicit binding 守恒：`context_selected=0 / invalid_selected=0`；Prompt manifest 的 rendered/reused Source identities 等于 `EVIDENCE_BUDGET.explicitCitationEligibleIdentities`；答案中的合法 `[n]` token 经 `CITATION_BINDING / S02_EXPLICIT_CITATION_BINDING_V1` 绑定后，`explicitCitationIdentities`、binding/FINALIZE/archive source snapshot 按 token 首次出现顺序一致。Context、未渲染 Source、未知/越界 token 和无稳定 identity 条目不得绑定；答案没有合法 token 时不得自动补引。每轮在 `records/S18.md` 记录 exchange、当前 task source identity、Prompt reference/manifest、parsed token、binding/rejection、final source identity和人工质量观察；人工事实支持性不单独决定 `BLOCKING_FAIL`。

确定性失败按已确认层级路由：构建产物违反 S10/S11 已确认契约或缺失 source span/identity -> S10/S11/S17；合法 Source 已进入统一候选却被窗口/final policy 以违反明确排序契约的方式过滤 -> S07-S09；Source/Context 物理分池或 capability 越界 -> S03；合法 token 解析、binding/rejection、首次出现顺序、FINALIZE/archive source snapshot 守恒回归 -> S02。引用已合法绑定但答案仍不受原文充分支持时只记模型生成/citation 覆盖观察，不创建 Prompt、S15 或 NLI repair owner。S18 只对已证实的确定性错误定位 owner；不现场调权重、扩大 topK、修改 parser 或补业务规则。

终验不变量：

- `context_only selected = 0`。
- Plan/request scope 与 channel 实际执行一致。
- 已由确定性 policy 选中的 Source 必须进入 Prompt；相关原文是否被模型召回/排序到预算内，在没有已确认项目特有确定性偏差时只作质量观察。
- Prompt rendered/reused Source identities = `explicitCitationEligibleIdentities`。
- 合法 `[n]` token 经 `CITATION_BINDING` 进入 final source snapshot；explicit/binding/FINALIZE/archive identity 及顺序守恒。
- Context、未渲染 Source、未知/越界 token 和无稳定 identity 不得绑定；无合法 token 时不得自动补引。
- 人工依据实际 Source 原文记录 citation 语义覆盖和答案事实质量；该记录不替代合法 token binding 权威，也不单独构成阻断。
- channel 聚合与 candidate 行守恒。
- 结构/table/KG/RAPTOR 均引用 S17 当前 task 产物。
- 表格构建产物、scope、identity、Prompt visibility 和 final/archive 守恒按确定性契约判定；问法级 table channel/答案覆盖差异按 `OBSERVATION_ONLY` 记录。

规则：

- 本阶段只验收，不现场补业务词、调权重或改规则。
- 48 个真实 case 的首次覆盖由用户执行；AI 只读判定，不能使用 S17 前旧 exchange、未审计 exchange 或自行制造的新 exchange 代替。完整 cohort 已审计后，后续窄范围修复可以按下述影响分析保留未受影响 case 的历史执行证据。
- 单次失败先区分用户操作/会话分组/问题文本错误、服务/模型/外部依赖临时失败、S18 cohort 版本/水位/知识库选择失效、验收 SQL/JSON 路径/日志查询错误，以及稳定可复现的生产行为回归。前四类按事实使 S18 保持 `IN_PROGRESS`、进入 `HUMAN_ACTION_REQUIRED` 或 `BLOCKED`，不得机械重开前置阶段。
- 只有当前源码、O9、数据库和稳定反例确认某个已 `DONE` owner 的结论失效，才停止 S18，按 改造计划与进度 的 `DONE -> REOPENED` 协议移交该 owner，并在新的阶段会话修复。
- 代码、Prompt、配置或构建产物变化后必须先冻结差异并给出可审计的影响范围。未受影响且已经完整审计的 case 可以继续作为历史执行证据；受影响的确定性契约必须由中性 fixture、受影响自动回归和至少一个运行新代码的真实 exchange 闭环。只有影响范围无法界定、变化横跨多个主链 authority、或既有证据不足以证明未受影响时，才要求全量重跑 S18。
- 构建产物变化必须重新验收受影响的 S17 document/task 及其对话 case；构建契约或全部 15 份产物的共同 producer 变化且无法缩小影响范围时，才重新执行完整 S17/S18。纯运行时窄修复不得仅因 Git 或 class hash 变化机械作废固定文档、其他 authority 或已审计的模型质量观察。
- 只有 48 个用例首次覆盖记录完整、受影响修复有新代码关闭证据、确定性 `BLOCKING_FAIL=0`、所有 P0 authority/invariant 通过、全量测试和门禁绿色，才能把全部计划标记为 `DONE`；`OBSERVATION_ONLY` 不阻塞完成。
