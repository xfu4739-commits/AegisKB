## 1. 计划来源

本计划不是从功能清单反推出来的包装文档，而是从遗留项目中的确定性问题逐步形成：Prompt 可见证据与最终引用候选不一致、Source 与 Context 职责混淆、检索计划存在多个解释点、fusion/rerank/final selection 多层决策、Markdown 结构被压平、GraphRAG 抽取包含样例语义、构建状态缺少单一权威，以及 O9 统计与最终归档不能完整守恒。

设计过程采用以下推导链：

```text
旧项目问题
-> 当前源码、测试和运行数据
-> producer / transition / consumer 事实追踪
-> 业务与技术不变量
-> 候选方案比较
-> 项目设计决策
-> characterization fixture
-> 目标失败测试
-> 分阶段实施
-> 自动验证与真实产品验收
-> 执行记录和必要的阶段重开
```

问题事实、阶段归属和总体架构摘要见本文件下方的“问题基线与阶段归属”和“目标架构与权威边界”；详细证据进入对应阶段和执行记录，通用验证口径见 [验证规则.md](验证规则.md)。

### 1.1 问题基线与阶段归属

本计划从当前源码、测试、数据库记录、旧 exchange、解析产物和只读运行复核中推导，不从功能清单反推。关键事实先标记证据等级：`CONFIRMED`、`CODE_CONFIRMED`、`DATA_CONFIRMED`、`STRONG_INFERENCE` 或 `HYPOTHESIS`；未经核验的 `HYPOTHESIS` 不能驱动长期或不可逆实现。

| 已确认的问题 | 设计方向 | 责任阶段 |
| :--- | :--- | :--- |
| Prompt 可见 Source 与最终引用候选不一致 | 以同轮 Prompt manifest 建立显式引用资格和 token binding | S01-S03、S16 |
| Source Evidence 与 Context Only 只有标签没有硬边界 | 物理分池，Context 不得进入 final evidence 或 archive | S03 |
| RetrievalPlan、会话计划、route 和 Provider 多次解释同一范围 | Plan 一次授权，每个子问题生成唯一 execution request | S04-S06 |

| GraphRAG 抽取和构建混入样例语义且存在多权威 | Python 返回带证据候选，Java 拥有契约校验、构建状态和持久化 | S13-S14 |

### 1.2 目标架构与权威边界

目标主链路如下：

```text
用户选择知识范围
-> Query Understanding 提供建议
-> RetrievalPlanAssembler 冻结唯一 RetrievalPlan
-> RetrievalExecutionRequest 薄投影
-> Vector / Keyword / Table / GraphRAG / RAPTOR Provider
-> Hybrid Fusion 统一候选与特征
-> Source Ranking Window
-> Rerank
-> Final Evidence Selection Policy
-> Source Evidence / Context Only 分池
-> Prompt Evidence Manifest
-> Answer Generation
-> Explicit Citation Binding
-> FINALIZE / Archive / O9 守恒
```

Java 拥有知识范围、任务状态、RetrievalPlan、检索编排、fusion/rerank、最终 Source Evidence、Prompt、显式引用、归档和 O9；Python 只承担 Markdown/OCR/layout/table、模型推理、rerank、通用 GraphRAG/RAPTOR 等工具能力。Python 返回候选、分数、source span、quote 和算法状态，但不决定业务 scope、route、最终证据、答案、引用或业务库状态。

| 决策 | 唯一权威 | 其他组件只允许做什么 |
| :--- | :--- | :--- |
| hard scope | 用户选择快照 + `RetrievalPlanAssembler` | advisor 提建议；Provider 投影和执行 |
| route/channel | `RetrievalPlan` | execution request 携带，Provider 消费 |
| fusion 特征 | `HybridFusionService` | 生成统一候选，不做最终保留 |
| rerank 窗口和排序 | `SourceRankingWindow` + `RagRerankService` | 截取稳定窗口并记录排序或降级 |
| 最终 Source | `FinalEvidenceSelectionPolicy` | 只消费 Source，不消费 Context |
| Prompt 资格 | Prompt Evidence Manifest | 只渲染合格 Source，Context 保持独立 |
| 最终 citation | `ExplicitCitationBindingService` | 只解析合法同轮 `[n]` token |
| GraphRAG 构建 outcome | Java 构建权威 | Python 返回算法候选和状态 |
| 归档来源 | FINALIZE 后的 explicit identities | archive 不重新选择来源 |

## 5. 机器可读重开状态

下列块与上方状态表共同属于本文件的唯一状态权威。当前所有重开均已关闭：

```json
{
  "schemaVersion": "rag-stage-reopen-baseline.v1",
  "activeReopen": null,
  "suspendedReopen": null
}
```

正常重开时，必须在同一次《改造计划与进度》修改中写入 `{ownerStage, ownerPreviousStatus, previousCurrentStage, reopenedAt, successorBaseline}`。`ownerPreviousStatus` 只能是 `DONE`；active owner 必须成为 `currentStage`；所有 successor 在 owner 完成前必须保持 baseline 状态。只允许一个 active reopen；需要回到更早 owner 时，现有 descriptor 进入唯一 `suspendedReopen`。没有完整退出证据不得清空 descriptor。

## 7. 状态生命周期

阶段状态只允许：

- `NOT_STARTED`：尚未进入实现。
- `IN_PROGRESS`：已经修改测试或实现，但退出条件未满足。
- `HUMAN_ACTION_REQUIRED`：自动工作完成，等待用户执行真实产品操作。
- `BLOCKED`：已复现外部阻塞，当前不能继续。
- `DONE`：退出条件和 record 证据全部完成。
- `REOPENED`：后续证据推翻已经完成的前置 owner。

一个会话只执行一个阶段；一个阶段可以跨多个会话。普通阶段按 `NOT_STARTED -> IN_PROGRESS -> DONE` 运行。真实操作按 `IN_PROGRESS -> HUMAN_ACTION_REQUIRED -> IN_PROGRESS -> DONE` 运行。已经完成的 owner 被推翻时按 `DONE -> REOPENED -> IN_PROGRESS -> DONE` 运行。发现当前未完成阶段自身问题时只能保持 `IN_PROGRESS` 或进入 `BLOCKED`，不能直接改为 `REOPENED`。

## 8. 确定性失败与模型观察

`BLOCKING_FAIL` 只用于能够定位到本项目 producer/transition/consumer 的确定性违规，例如：

- hard scope 被错误扩大或收窄；
- suggestion 越权成为 hard constraint；
- 普通召回被可选增强清空；
- ranking/final policy 违反已确认的分数、窗口或预算契约；
- 错误构建产物被权威链路消费；
- Context、未渲染 Source、未知或越界 token 被实际绑定；
- binding、FINALIZE 和 archive identity 不守恒。

当 scope、Plan/request、证据资格、显式引用和 O9 均合法时，模型漏意图、答反、遗漏、措辞、表格口径、复杂关系综合或引用覆盖不足只记 `OBSERVATION_ONLY`，不能据此增加业务词规则、样例 adapter 或重开阶段。
